# 企业规则与例外（business rules）

> **版本**：`rules-v1` ｜ **本体版本**：`onto-v1` ｜ **更新日期**：2026-08-31
> **消费方**：全体成员 Agent（`contract-intake` / `clause-extractor` / `risk-scanner` /
> `jurisdiction-auditor` / `review-reporter`）
>
> 本文件是**人类可读、可 diff、可回滚**的规则载体（蓝本第十五节「经验固化」）。
> 它与 `jurisdiction-packs/` 的分工是：
> - `jurisdiction-packs/` 管**法律与市场层面**的规则（法条、行业标尺、企业红线数值）
> - 本文件管**流程与协作层面**的规则（谁在什么时候能说什么话、例外怎么走）
>
> 修改本文件必须：① 在「变更记录」追加一行；② 若改动影响判定结果，在
> `test-cases/` 增加或更新回归样本；③ 经用户确认后生效——**Agent 不得自行改写本文件**。

---

## 0. 规则的读法

每条规则的格式固定为五段。缺任何一段的规则视为草稿，不生效。

| 段 | 含义 |
|---|---|
| **规则** | 一句话陈述，必须可判定真假 |
| **理由** | 为什么需要它。理由缺失的规则无法被正确地例外化，也无法被安全地删除 |
| **例外** | 明确列举；写「视情况」等于没写。无例外时写「无」 |
| **违反时** | `block`（阻断）/ `failure_mark`（记欠账）/ `flag`（提示）/ `reject_output`（拒收该输出） |
| **来源** | 蓝本章节或历史错误样本编号，用于回溯这条规则是被什么教训换来的 |

## 1. 流程规则

### R-001 工具链顺序固定，不得由模型自行编排

- **规则**：审查必须严格按 7 步执行：结构化解析 → 完整性检查 → 条款抽取 → 法域知识注入 → 风险判读 → 版本对比 → 报告输出。不得跳步、并步或调序。
- **理由**：打乱顺序会让过程无法被他人复现，只能依赖个人记忆。可复现性是本团队区别于「一次模型输出」的根本。
- **例外**：第 6 步版本对比在只有单一版本且无历史基线时可标记为 `not_applicable`，但必须在报告中显式记录，不得静默跳过。
- **违反时**：`reject_output`（报告 Agent 拒收未按序产出的中间件）
- **来源**：蓝本第三节

### R-002 识别与复核必须由不同 Agent 执行

- **规则**：产出结论的 Agent 不得自检该结论；复核由 `review-reporter` 独立完成。
- **理由**：一个 Agent 既产出又自检，等于把错误一起签收。
- **例外**：无。
- **违反时**：`reject_output`
- **来源**：蓝本第二节

### R-003 复核 Agent 不读前序推理

- **规则**：`review-reporter` 的输入只允许包含：原文、结构化事实（`clause` / `contract_document` / 边集合）、规则集、覆盖矩阵骨架。**禁止**包含前序 Agent 的推理过程、理由陈述、置信度自评与结论草稿。
- **理由**：读到前序推理会触发自我确认——复核退化成复述。
- **例外**：可读取前序 Agent 的 `failure_mark`（那是事实，不是推理）。
- **违反时**：`reject_output`
- **来源**：蓝本第二节 / 第十四节

### R-004 交接使用结构化载荷，不传对话历史

- **规则**：Agent 间交接只允许四段：**交接对象编号**（`object_ref` 三元组 + `manifest_digest`）、**已确认事项**、**待确认项**、**本次任务范围**。
- **理由**：传整段历史会把上游的措辞、犹豫与错误一并带入下游，且无法审计到底传了什么。
- **例外**：无。
- **违反时**：`reject_output`
- **来源**：蓝本第十四节

### R-005 每次任务写回执

- **规则**：每个 Agent 完成任务必须写 `receipt`（对象版本、规则版本、证据位置、执行 Agent、人工确认点）。
- **理由**：规则更新后要做历史任务回放与差异对比，回执是唯一输入。没有回执，规则改进就无法验证是否真的修好了旧错误。
- **例外**：无。
- **违反时**：`block`（下一步不得启动）
- **来源**：蓝本第十四节

## 2. 事实一致性规则

### R-010 同一对象判定用三元组，不用编号

- **规则**：判断两个 Agent 是否在处理同一对象，必须比对 `object_id` + `version_label` + `content_digest` 全等。
- **理由**：编号相同而内容不同，正是「主合同已更新、附件仍是旧版」这一失败样态的入口。
- **例外**：无。
- **违反时**：`block`
- **来源**：蓝本第十四节 / 样本 `TC-001`

### R-011 未知必须显式，不得用空值表达

- **规则**：任何未确认字段写 `unknown` 并附 `*_unknown_reason`；禁止空字符串、`null`、省略字段、「无」「暂无」。
- **理由**：空值在下游被读成「已确认为空」。「没查到签署日期」与「确认无需签署日期」在结论上是相反的。
- **例外**：数组类字段「已检查且确实为空」时写空数组 `[]`，但必须写出该字段，不得省略。
- **违反时**：`block`
- **来源**：蓝本第四节 / 样本 `TC-003`

### R-012 无锚点结论一律不合格

- **规则**：任何非 `blank` 的结论必须携带完整四元组：条款编号 + 页码证据 + 结论等级 + 对应动作。
- **理由**：「综合来看风险较高」无法被复核，也无法被人工快速定位，等于没有产出。
- **例外**：整份文档级别的结论（如「本合同未约定争议解决条款」）允许 `clause_no = not_present`，但必须给出检索范围与已检索页码区间。
- **违反时**：`reject_output`
- **来源**：蓝本第七节 / 样本 `TC-005`

### R-013 未冻结不出一致性结论

- **规则**：主版本、附件清单、页码范围、签章状态四项未全部冻结时，禁止输出「一致」「无差异」「版本相同」类结论，`risk_direction` 只能是 `undetermined`。
- **理由**：差异数量为零不代表没有问题；在未冻结的基线上算出的零差异毫无意义。
- **例外**：无。
- **违反时**：`block`
- **来源**：蓝本第九节 / 样本 `TC-001`

### R-014 覆盖矩阵留白不得并入通过

- **规则**：`status = blank` 与 `status = blocked` 的检查项必须在报告正文单列，禁止计入通过率、禁止在摘要中省略。
- **理由**：欠账表的全部价值在于显式留白。合并进通过后，报告看上去更漂亮，而漏检恰好被藏在这里。
- **例外**：无。
- **违反时**：`reject_output`
- **来源**：蓝本第十五节 / 样本 `TC-006`

## 3. 阻断规则（不是「注意风险后继续」）

### R-020 五类输入缺陷直接拒绝

- **规则**：命中以下任一项，输入治理裁决为 `reject`，后续 Agent 一律不启动：
  1. 空字段占位符（`$X`、`TBD`、`[金额]`、`____`、`【待定】` 及同类）
  2. 缺失附件（正文引用但清单没有，或清单列明但文件未取得）
  3. 签署状态未确认（缺签章 / 缺日期 / 缺签署人 / 电子签名未核验）
  4. 页数不完整或页码范围不连续
  5. 角色身份不明（当事方名称前后不一致且未归并）
- **理由**：这五项决定「这份文件是不是一个可审查的对象」。在不成立的对象上做风险评分，是把不确定性洗成了确定性。
- **例外**：**条件通过**仅适用于以下情形，且必须在报告首页列明限制：缺陷仅存在于与本次审查范围无关的附件上，且该附件未被正文任何条款引用（`references` 边为空）。除此之外无例外。
- **违反时**：`block`
- **来源**：蓝本第四节 / 样本 `TC-003`

### R-021 法域包与法域线索不一致时阻断

- **规则**：`jurisdiction_pack_version` 声明的法域必须覆盖文档 `jurisdiction_clues` 中出现的全部法域线索，否则阻断。
- **理由**：用中国法包审一份约定纽约州法的合同，输出格式完整、内容整体无效——这类错误从报告表面看不出来。
- **例外**：合同未明示准据法时，允许以各方注册地推定并加载对应包，但必须在报告中标注「准据法未明示，按注册地推定」并触发人工确认。
- **违反时**：`block`
- **来源**：蓝本第八节 / 样本 `TC-004`

### R-022 版本矩阵不一致输出对齐建议，不自动放行

- **规则**：版本矩阵任一维度不一致，按该维度的 `on_mismatch` 处理（重跑 / 人工确认 / 重算历史样本 / 阻断 / 不复用旧结论），并输出「数据对齐建议」。
- **理由**：自动放行会让「规则已变但系统用旧建议」悄悄发生。
- **例外**：无。
- **违反时**：`block`
- **来源**：蓝本第八节

## 4. 人工签核规则

### R-030 法务四类不可替代动作必须过 Human Gate

- **规则**：涉及 ① 付款触发与回款 ② 争议解决机制 ③ 责任违约分配 ④ 生效要件 的任何结论与动作，必须触发对应 Human Gate；未取得确认前不得输出「可放行」。
- **理由**：这四类是法律效力与商业条件的定性点，系统提供证据，人负责定性。
- **例外**：无。
- **违反时**：`block`
- **来源**：蓝本第十二节

### R-031 Human Gate 不满足则退回重审，不做默认通过

- **规则**：Human Gate 的前置条件不满足时，动作结果为 `returned_for_rereview`，不得降级为「提示后继续」，也不得因超时而默认通过。
- **理由**：默认通过会把「没人看」等价于「看过了没问题」。
- **例外**：无。
- **违反时**：`block`
- **来源**：蓝本第十二节

### R-032 评分区间对应固定动作

- **规则**：总分对应动作固定为：88-100 可放行至法务确认（仍需过签核点）｜74-87 可谈判项，先出修改建议｜60-73 关键修改后继续｜48-59 必须人工主导，暂停推进｜0-47 重建条款，重跑评审。
- **理由**：分数的意义在于映射到确定动作。没有固定映射的分数只是修辞。
- **例外**：无。分数落在 88-100 但存在任一未解决的 `severe` 结论或未通过的 Human Gate 时，动作**下调**至该结论对应的动作，取两者中更保守者。
- **违反时**：`reject_output`
- **来源**：蓝本第五节 / 第十二节

## 5. 风险方向规则

### R-040 版本对比必须输出风险变化方向

- **规则**：版本对比结果必须含 `risk_direction`（`up` / `down` / `flat` / `undetermined`）。
- **理由**：「差异为 0」反而隐藏最大风险——附件被替换而主版本未变时，系统默认包含附件，关键风险被漏掉。
- **例外**：无。
- **违反时**：`reject_output`
- **来源**：蓝本第九节 / 样本 `TC-001`

### R-041 风险上升时动作升级

- **规则**：新增或修改条款导致风险升级时，动作从「建议优化」升级为「先谈判」。
- **理由**：风险方向变化本身就是谈判筹码的变化，用同一档动作对待等于放弃这个信号。
- **例外**：无。
- **违反时**：`flag` + `reject_output`（若报告未升级动作）
- **来源**：蓝本第九节

## 6. 规则优先级与例外处理

### R-050 三层知识优先级：custom > jurisdiction > base

- **规则**：同一检查项被多层规则覆盖时，取优先级最高层的判定。`custom` 层通过 `overrides` 字段显式声明它覆盖了哪些 `base` / `jurisdiction` 规则 id。
- **理由**：企业红线通常比市场惯例更严；但覆盖必须显式，否则无法回答「为什么这次没按行业标尺判」。
- **例外**：`custom` 层**不得**放宽法域强制性规定。企业红线可以比法律更严，不能比法律更松——遇到 `custom` 试图放宽 `jurisdiction` 层标记为 `mandatory: true` 的规则时，以 `jurisdiction` 层为准并输出冲突提示。
- **违反时**：`flag` + 按 `jurisdiction` 层执行
- **来源**：蓝本第六节

### R-051 例外必须记名、记时、记范围

- **规则**：任何例外的适用必须记录：依据的规则 id、批准人、批准时间、适用范围（限本案件 / 限本客户 / 长期）。长期例外必须回写为 `custom` 层的一条正式规则，不得以口头例外长期存在。
- **理由**：口头例外会变成事实上的规则，但没有版本、没有 diff、没有回滚路径。
- **例外**：无。
- **违反时**：`failure_mark`
- **来源**：蓝本第十五节 经验固化

### R-052 一次纠正，下次自动执行

- **规则**：人工纠正过的判断，必须在同一工作日内固化为可 diff 的规则或样本文件（`custom/redlines.yaml` 新增条目，或 `test-cases/` 新增样本），并经用户确认后生效。
- **理由**：不固化的纠正会重复发生，团队的价值就退化成一次性输出。
- **例外**：纠正涉及个案商业判断而非普遍规则时，只写入 `test-cases/` 作为反例，不进 `custom`。
- **违反时**：`failure_mark`
- **来源**：蓝本第十五节

## 7. 边界规则

### R-060 Agent 提供证据与建议，不做定性与决策

- **规则**：报告用语必须是「建议 / 证据显示 / 需确认」，禁止使用「本合同合法有效」「可以签署」「无法律风险」这类定性表述。
- **理由**：法律效力终局判断、商业条件拍板、签章授权、对外承诺均不在能力边界内。
- **例外**：无。
- **违反时**：`reject_output`
- **来源**：蓝本第十七节

### R-061 不确定的法条不编造

- **规则**：引用法条时，条文序号与内容任一不确定，必须写成「需人工确认」并给出不确定的具体部分（如「内容确定，条文序号因法律修订可能变化，需人工确认」）。禁止编造条文编号、司法解释编号或判例名称。
- **理由**：一个错误的条文号会让整段结论在法务眼里失去可信度，且比不引用更糟。
- **例外**：无。
- **违反时**：`reject_output`
- **来源**：蓝本第十七节 / 样本 `TC-004`
